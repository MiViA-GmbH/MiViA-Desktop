# Generate the API client with progenitor after tolerant-reader spec patches

The Rust API client is generated by progenitor 0.15.1 in `build.rs` from a committed spec snapshot, after a patch step that, in order: drops multipart operations; adds `type: string` where a schema has `format` without `type`; removes `additionalProperties: false`; opens every string enum as `oneOf [known, any string]` (a single-value enum that discriminates a union stays closed); wraps every union of object branches in `oneOf [union, {}]`; and drops deprecated operations, parameters and properties. Without these patches the generated client compiles but rejects any new server field, enum value or result kind at runtime, and neither progenitor nor typify has a setting for a catch-all variant (typify #574).

## Considered Options

- typify types + hand-written reqwest calls: the same patches are still needed, more hand-written code, no compile-time link to paths.
- Hand-written serde types: what the .NET client did; its strict types caused most of its bug fixes.

## Consequences

- Generated enums are `Variant0(Known) / Variant1(String)` wrappers; the server adapter maps them to domain types with an explicit `Unknown`.
- Each patch rule is policy and has its own unit test. The `format` patch goes away once the server spec is fixed; the multipart patch once progenitor supports it.
- Upload (streaming multipart) is hand-written on the same HTTP client.
